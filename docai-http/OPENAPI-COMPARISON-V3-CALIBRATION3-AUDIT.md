# Calibration 3 Offline Audit

## Scope And Status

Audit date: 2026-11-10. This follows the failed
[Live calibration](OPENAPI-COMPARISON-V3-CALIBRATION3-RESULTS.md).
No inference request was made during this audit. No frozen package, prompt,
retained answer, gate, or Stable conformance artifact was changed.

The next calibration must address both false negatives and false positives
in evaluation, not merely make the observed answers pass. The current gate
remains failed. No primary schedule or public comparative claim is justified.

## Confirmed Findings

### 1. Output Schema Metadata Is Easily Confused With Answer Fields

The frozen `runtime/contract.mjs` function `buildRequiredOutputText()` prints
an object containing `schema_version` and `schema`. The actual answer schema
forbids a top-level `schema_version`. Adding that field to an otherwise valid
synthetic workflow answer produces `invalid-contract`.

This confirms an instruction/answer distinction that needs clarification,
not that the validator should accept arbitrary extra answer keys. All four
Anthropic workflow answers included the field; why the model chose it remains
an inference. A successor should display only the answer schema and explicitly
separate any contract metadata from the object to return.

### 2. Private Spellings And Layouts Cause False Negatives

The upload assertion requires exactly
`multipart/form-data; boundary=<library-generated>`. The supplied DocAI
document instead illustrates
`multipart/form-data; boundary=<generated by HTTP library>` and instructs the
caller to delegate boundary creation to its HTTP library. Copying that
documented symbolic spelling into a synthetic answer causes failure.
Neither spelling is an actual boundary to send on the wire. Conversely,
`multipart/form-data` alone does not prove that the library will manage the
boundary. The successor needs an explicit, testable representation of this
behavior rather than simply accepting every media-type string.

Workflow assertions also require:

- A flat `input` object for header/body values, although the public schema
  allows arbitrary JSON-valued properties and gives no location convention.
- The exact symbolic key `<payment-operation-key>` and `<order-operation-key>`.
- The case label `ambiguous/retryable POST /orders`, despite `case` being a
  free string in the public answer schema.

Those key spellings and that case label are absent from both the enriched
OpenAPI and selected DocAI workflow contexts. Synthetic answers that change
only these representation choices fail.

Not every comparison is over-strict: `header_contains` already accepts
case-insensitive header names and suitable nonempty idempotency-key values;
array containment ignores order. Preserve these correctly bounded allowances.

### 3. Generic Substring Containment Causes False Positives

In `runtime/grader.mjs`, `containsValue()` uses `String.includes()` for
strings. It recursively applies this to workflow paths, state labels and
other values. The schema also does not enforce unique step ordinals.

Starting from the canonical synthetic workflow answer, each of the following
mutations still passes all frozen assertions:

- Change the payment path to `/v1/payments/wrong`.
- Change the first success state to `not cart.validated`.
- Append a contradictory extra step with an existing step ordinal and
  path `/wrong`.

These are not acceptable semantic equivalents. A successor should use exact
comparison for wire paths and declared state identifiers, explicit set/list
semantics, and uniqueness/ordering checks. Broad fuzzy or substring matching
would preserve or expand this failure mode.

### 4. Fact Inventory Is Not Proof Of Measured Semantic Coverage

`documents:size-limits` is a required fact in the upload task inventory but
has no assertion. The public request answer schema has no dedicated size-limit
handling field. Thus passing that task would not establish correct size-limit
handling. Choose whether that fact belongs in the task's scored scope before
the successor is frozen; do not label it measured merely because it is loaded.

The parity builder assigns fact IDs from the task inventory and expected
missing-fact lists. Its checks verify those annotations, not the semantic
content of every supplied fact. In particular, the selected DocAI workflow
contains `cart.validated`, while the enriched OpenAPI/behavior context
describes validation in prose without that exact state label. Requiring the
DocAI spelling without a condition-neutral output convention can favor one
representation even when the behavior is described in both.

Retain the comparison between incomplete raw/sliced context and complete
contexts, but distinguish it from the same-information format comparison
between enriched OpenAPI and DocAI. A correct declaration of missing evidence
must be reported separately from successfully implementing the whole task.

### 5. Usage Normalization Must Be Provider-Specific

The frozen normalizer and dollar-stop calculation omit separately reported
Google thinking tokens. This affects the observed run, as documented in the
Live result. A synthetic Anthropic cache case also loses cache read/write
tokens from normalized totals. Its observed calibration cache counts were
zero, so this is a demonstrated latent case, not an additional observed bill.

Use provider-native usage components with explicit inclusion relationships:

- Google Interactions reports thinking separately; the combined generated
  budget includes thinking and final output. The observed incomplete workflow
  responses are consistent with exhausting that budget, but have no explicit
  retained stop reason. [Google thinking documentation](https://ai.google.dev/gemini-api/docs/thinking)
- Anthropic input accounting includes uncached, cache-write and cache-read
  components; cost must retain their separate billing categories.
  [Claude prompt caching documentation](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- OpenAI reasoning is already part of reported output usage. Do not add it
  again when summing billable generated tokens.
  [OpenAI reasoning documentation](https://developers.openai.com/api/docs/guides/reasoning)

These references were checked on the audit date. Revalidate model-specific
rates, cache behavior and limits during successor preparation. Preserve raw
usage, normalized usage, estimated charge and actual invoiced charge as
distinct concepts; an incomplete response can still incur usage charges.

## Successor Approach Decision

The maintainer selected **A: an explicit structured semantic answer contract**
on 2026-11-10. The [detailed successor design](OPENAPI-COMPARISON-V3-CALIBRATION4-DESIGN.md)
has also been approved. The [implementation plan](OPENAPI-COMPARISON-V3-CALIBRATION4-PLAN.md)
awaits maintainer review and execution-method confirmation, not authorization to send.

| Approach | Advantages | Disadvantages |
|---|---|---|
| A. Structured semantic contract with deterministic grading | Makes answer locations, symbolic inputs, state/case vocabularies and safe-retry predicates public; rejects wrong wire values and contradictions without judging prose; reproducible across providers | Measures constrained client-planning rather than unconstrained prose/code generation; the public contract adds tokens that must be counted |
| B. Keep free-form fields and extend deterministic equivalence rules | Retains more natural responses; can accommodate known alternate representations | Synonym/layout coverage is difficult to bound; silent false passes and false rejects remain a measurement risk |
| C. Use a separate LLM judge for free-form semantics | Can interpret varied language and layouts | Adds judge bias, variability, cost and another model dependency; requires its own human calibration and audit |

A should expose only generic answer conventions, not task-specific answers
or missing API facts. For example, a generic boundary-management property can
express delegation versus a hard-coded boundary; the documentation must still
determine which behavior applies. Keep rationale prose separate from scored
operational fields. Define explicit unknown states and distinguish unknown
evidence from asserting an unsafe action.

With the detailed design approved, review its implementation plan before
implementation. Include permanent positive/negative tests
for the cases above, source-to-assertion coverage review, Google output-budget
options and provider-specific billing accounting. Model and budget choices
must be included in the later exact execution envelope. Keep the gate's
23-decision/one-exception threshold unless a separately justified, prospectively
approved methodology change is made; do not loosen it to fit these results.

Live execution remains blocked pending a new freeze and separate approval.
