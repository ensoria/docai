# Source Traceability — Incomplete Audit

This audit covers the `0.17.1` complete candidate's `full/` and `compact/` roots. JSON locations are JSON Pointers relative to the named source. The five prerequisite gaps recorded below have been addressed with explicit synthetic-source facts and projection tests. The full audit and release gate remain incomplete; this file does **not** certify release readiness.

## Authority and Checker Boundary

The authoritative input set is the four sources bound by `source/projection-input-manifest.json`: `storefront.asyncapi.json`, `storefront-behavior.json`, `complete-contexts.json`, and `complete-representations.json`. The manifest establishes perspective, precedence, adapter mappings, and projection identity. Existing output and literal test expectations are evidence of current rendering, not additional source authority.

`tools/check-complete-fixtures.mjs` validates document structure, identity, and full/compact equivalence. For this versioned candidate it also checks the exact bytes of all four manifest-declared source files and selected source-to-output facts in both profiles. `tools/tests/complete-candidate.test.mjs` checks further source bindings and projected facts. None of these checks proves that every emitted semantic fact has authoritative support. A matching pair can repeat the same unsupported assertion in both profiles.

`tools/tests/complete-source-projection.test.mjs` compares synthetic source identities, payload absence, scoped operation defaults, purposes, expanded Workflow coordination facts, and explicit variant schemas against parsed output in both profiles, expanding compact forms first. It also checks that the storefront send purpose retains the sourced distinction between command acceptance and final fulfillment. It checks closed roots independently of pair equality and verifies rejection of extra decoded properties in CSV and variant examples. The candidate-specific CLI audit repeats the directly comparable facts as a read-only gate, with additional manifest source-byte, perspective, version, Sources catalog row/provenance, storefront operation route/summary/identity/purpose/Behavior/Reply envelope/operation-specific Failure Handling, incomplete Workflow state mappings, and fifteen CONVENTIONS section checks. It is not a general source-aware converter.

The CLI gate deliberately does not yet compare every source fact. Convention dependency closure still requires fact-by-fact review and further source-aware checks. The compact representative-policy gate described below preserves the candidate's required reduction examples, separately from source authority and token measurement. All fifteen storefront CONVENTIONS sections are checked against the current candidate's known source facts in both profiles. Their comparison covers complete section content or exact parsed table rows with no trailing prose, not just the presence of a source keyword. Environments, Protocols and Bindings, and Serialization additionally compare the corresponding AsyncAPI and behavior facts, including the selected messages' media types. Authentication compares behavior's scheme, acquisition, rotation, and operation authorization with each AsyncAPI operation's OAuth2 client-credentials flow, token URL, and selected scopes. The separate operation-body Behavior gate compares all six lines for both storefront operations and requires each authorization sentence to agree with that operation's single declared scope; this is candidate-specific and does not establish a general multi-scope rendering policy. The Reply envelope gate checks the RECEIVE known absence and the SEND channel, correlation, timeout, empty reply Channel subsections, selected Message identity, and `reply:` INDEX entry against behavior and AsyncAPI sources. The separate storefront Message gate checks the primary and reply schema cells, explicit field descriptions, and payload example values described below. The separate local-binding gate certifies only the current known-absence scope described below. Error Handling compares the shared behavior failure-recovery policy, including the candidate's five-attempt wording and dead-letter destination. The separate operation-specific Failure Handling gate compares the exact `Failure | Signal | Condition | Action` rows, count, order, and absence of trailing content against both `operationFailures` arrays; it does not infer a general failure-shape projection policy. The incomplete Workflow gate compares all four section bodies, source routing names and purposes, and per-file completeness for the `none`, `unknown`, and `unsupported` cases. The Reference Material gate checks the sole source entry's no-authority marker, info string, exact BOM/line-ending-normalized content, minimal backtick fence, supplemental-only consumer, and `complete-contexts` provenance in both profiles. It does not establish a general reference projector or focused invalid rejection corpus. Request-Reply compares the shared behavior channel, correlation, and deadline/outcome with the AsyncAPI reply channel address. Schema Evolution compares behavior's compatibility policy, logical API identity, and contract version with AsyncAPI `id` and `info.version`; missing-identity/version marker scenarios are not present in this candidate. Candidate-specific prose normalization must be reviewed with any deliberate source wording change. The Sources `source_refs` check is exact for this four-source scenario, in which each catalog row is supplied by its own source; it is not a general rule that forbids cross-source catalog-cell contributors. Passing the gate is not a release-readiness certificate.

The storefront Message gate covers `CreateOrder`, `OrderCreated`, and the embedded Reply `OrderAccepted` in both profiles after compact expansion. It checks named header/field inventories, logical types, direction-specific Required/Presence, non-nullability, the current constraint fragments, explicit closed payload-object rows including array items, whole-payload markers, and exact decoded payload example values. Source schemas and examples are parsed without numeric narrowing. This is a finite candidate policy for the current closed object/array/scalar shapes and `const`, `format`, `minimum`, `minLength`, `pattern`, and `minItems` vocabulary; unfamiliar schema features fail this audit rather than being silently ignored. Header-map root closure is a source prerequisite; it is not represented by a payload-style `$` row. Field prose is compared to explicit source descriptions as detailed below; non-emitted source header examples remain outside this gate's certification. A source-policy extension needs explicit review.

The storefront field-prose checkpoint adds 17 explicit schema `description` values as authored synthetic scenario facts approved for this candidate: six header meanings and eleven payload-field meanings, including the `items` container and its child fields. These descriptions are not inferred by the checker from field names, types, examples, or existing output. The gate compares the description exactly after ordinary table decoding, including escaped pipes and permitted output-cell boundary spaces. Missing descriptions authorize no descriptive prose; object closure is independently derived from `additionalProperties=false` and appended after any description. Non-string and multiline descriptions fail this finite audit, as does a non-empty header-map root description because there is no projected root row. This does not establish a general prose renderer, a paraphrase-equivalence algorithm, or a schema-to-document converter.

The synthetic representation gate checks the exact six-operation source inventory and projected inventory in `channels/representations.md`, routes and Message identities, declared form, payload presence/nullability/media markers, direct schema target, and current schemas with exact field descriptions. Its finite schema policy permits closed objects with named non-null string fields and optional string `const`; unknown schema features and non-string `required` entries fail the audit. Tagged discriminator/value markers and untagged labels/selection prose are compared to source, as are opaque-raw form and description. CSV source adapter metadata must match the trusted publication adapter and its one-object decoding model. CSV examples are compared after trusted decoding, while JSON and variant examples use exact decoded JSON values. Each reused JSON operation is checked against its own source after compact expansion. The existing canonical representation view normalizes prose trailing spaces and excludes `x-` extensions, including their fenced data, before auditing standard contract content. This does not certify a general schema converter, arbitrary variant classifiers, compact token savings, or convention dependency closure.

The local-binding gate checks the two storefront Operation Bindings units, two primary Channel Bindings units, and three primary/reply Message Bindings units. An omitted `bindings` member or an explicit empty top-level binding map establishes no local addition in this candidate's authoritative AsyncAPI input; applicable CONVENTIONS still apply. Null, arrays, strings, non-empty protocol maps (even an empty per-protocol object), and binding references do not establish that absence. The corresponding normalized output must retain `none`, with primary Channel Bindings accepted in either permitted collapsed or headed form. Both the Message schema/example and binding audits follow the operation's explicit primary/reply selection through local references to the selected Message, rather than assuming a component key from its displayed name. An equivalent alternate Reply component is permitted; stale contracts behind it are not. The gate does not certify non-empty binding projection or Channel Parameters; field prose is owned by the Message schema audit. The existing Reply Channel gate remains separate. Ordinary validation currently rejects an `x-` marker after binding `none`; this preexisting extension-handling gap is recorded in TODO and is not repaired by the source audit.

The earlier Core [source audit](../../core/v0.17.1/SOURCE-TRACEABILITY.md) documents the storefront contract mappings. Its behavior input is retained unchanged; the candidate-local AsyncAPI now additionally declares field descriptions. The Core input and corpus are unchanged. Its Core-specific claims about source array positions, flat routing, empty contexts, all-file completeness, and `source_refs: all` do not transfer to this candidate.

## Compact Representative Policy and Measurement Boundary

`tools/lib/complete-compact-policy-audit.mjs` is a finite retention gate for this versioned complete candidate, not a source schema adapter. After ordinary profile-pair validation and source auditing succeed, the CLI applies it only to a candidate with the `docai-messaging-complete-fixture-projector` identity. The gate uses existing field-default and same-as facts plus bounded representation/fence parsing to require the original operation's single-line JSON example and two-column defaults, the reuse operation's direct reference to that original representation, and its channel-file retrieval metadata in `channels/representations.md`. Moving a representative elsewhere, expanding away the last required example, or replacing it with a literal inside an `x-` fence does not retain the intended coverage. Valid extra defaults, equivalent JSON object order/escape/whitespace spellings, and non-contract extensions remain allowed. Failures use the separate `Complete compact policy:` prefix, not a source-fact or ordinary conformance diagnostic.

The corresponding full representations and each operation's independent source contract are already checked by the existing pair and source gates; this policy does not recreate their expansion or equality logic. It establishes neither a general readability classifier nor measured optimal rendering. Under README §3.4, the savings conditions for compact examples, defaults, same-as plus retrieval cost, sharding, and selective conventions remain producer assertions for an ordinary set. No compact savings, total-task token improvement, or release readiness is claimed here. Task 14 still owns the §6.2 tokenizer, baseline, task corpus, fallback costs, regressions, and p50/p95/maximum evidence; convention dependency closure remains a separate Task 12 checkpoint.
