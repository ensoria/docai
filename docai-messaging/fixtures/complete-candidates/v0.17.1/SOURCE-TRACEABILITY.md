# Source Traceability — Incomplete Audit

This audit covers the `0.17.1` complete candidate's `full/` and `compact/` roots. JSON locations are JSON Pointers relative to the named source. The five prerequisite gaps recorded below have been addressed with explicit synthetic-source facts and projection tests. The full audit and release gate remain incomplete; this file does **not** certify release readiness.

## Authority and Checker Boundary

The authoritative input set is the four sources bound by `source/projection-input-manifest.json`: `storefront.asyncapi.json`, `storefront-behavior.json`, `complete-contexts.json`, and `complete-representations.json`. The manifest establishes perspective, precedence, adapter mappings, and projection identity. Existing output and literal test expectations are evidence of current rendering, not additional source authority.

`tools/check-complete-fixtures.mjs` validates document structure, identity, and full/compact equivalence. For this versioned candidate it also checks the exact bytes of all four manifest-declared source files and selected source-to-output facts in both profiles. `tools/tests/complete-candidate.test.mjs` checks further source bindings and projected facts. None of these checks proves that every emitted semantic fact has authoritative support. A matching pair can repeat the same unsupported assertion in both profiles.

`tools/tests/complete-source-projection.test.mjs` compares synthetic source identities, payload absence, scoped operation defaults, purposes, expanded Workflow coordination facts, and explicit variant schemas against parsed output in both profiles, expanding compact forms first. It also checks that the storefront send purpose retains the sourced distinction between command acceptance and final fulfillment. It checks closed roots independently of pair equality and verifies rejection of extra decoded properties in CSV and variant examples. The candidate-specific CLI audit repeats the directly comparable facts as a read-only gate, with additional manifest source-byte, perspective, version, Sources catalog row/provenance, storefront operation route/summary/identity/purpose/Behavior/Reply envelope/operation-specific Failure Handling, incomplete Workflow state mappings, and fifteen CONVENTIONS section checks. It is not a general source-aware converter.

The CLI gate deliberately does not yet compare every source fact. The final fact-by-fact matrix review remains incomplete. The finite convention-closure gate described below now checks the candidate's declared dependency inputs and conservative fallbacks. The compact representative-policy gate described below preserves the candidate's required reduction examples, separately from source authority and token measurement. Their comparison covers complete section content or exact parsed table rows with no trailing prose, not just the presence of a source keyword. ## Whole-Candidate Operation Inventory

Malformed inventory containers or non-string/empty identities do not establish an empty inventory. Behavior entries, operationContracts, and dependency maps attach facts to owners; they do not introduce additional operation owners. An embedded Reply remains a Message, not an invented operation.

After source-byte/identity binding checks, the CLI preflights **both** profiles before dependent semantic audits. It compares the sorted source union to routing row names and operation definition names, and requires every `channels/` file to be owned by routing. This last check matters because Core collects operation definitions only from routed channel paths; a matching parsed inventory alone would miss an operation in an entirely unrouted file. It does not rely on one channel file, the other profile, a fixed count of eleven, or current literal operation names. Ordinary validation continues to own row/definition uniqueness and structural correspondence; the existing representation-file inventory gate remains in force after preflight. Workflow step references, fenced Reference Material and extension data are not separate normal-operation definitions. CLI tests cover unowned operations in two routed files, same-cardinality owner replacement, duplicate source ownership, two unrouted-file cases (new or already known name), and early rejection before malformed missing-owner semantics. A properly sourced additional context operation and a relocated routed channel file remain valid. The pure collector tests cover union ordering, all three cross-source collision pairs, repeated entries and malformed inventories.

This is the finite positive candidate's policy that every declared operation is projected normally, not a general rule that all arbitrary source operations must have normal rows. Generation failures, Unprojected Operations and other source selection outcomes retain their separate corpus responsibilities. Source, manifest and projection bytes are unchanged by this gate; no projector-version change or restamp is required. This resolves only the inventory portion of MATRIX-001. The storefront context known-absence policy remains open, as do MATRIX-002–005 and Task 12 overall.

## Structured Convention Dependency Proof

The two synthetic sources now author `conventionDependencies` as separate `operations`, `workflows`, and `sections` maps. The operation/workflow inventories must match their source scopes exactly. Their direct dependencies are unique arrays of exact convention headings; `[]` explicitly establishes no direct addition, while `null` means unknown. Missing records and malformed values do not establish absence. Context operations and workflow coordination declare no direct convention additions; representation operations declare `Data Representation`, whose additional section edges are explicitly empty. No other section has an invented empty edge list. Incomplete Workflow section knowledge remains incomplete: a direct convention-needs declaration is not proof of workflow readiness.

The source-aware helper computes the union of an operation's direct needs, every required workflow's direct needs, and the needs of operations used by that workflow's exact source Steps. Expanded workflow sources require a Steps array; section-state sources prove an empty step sequence only through explicit `sections.Steps: "none"`, without a competing top-level `steps` member. Unknown, unsupported, missing, or ambiguous Steps do not prove an empty sequence. Required-workflow links and section-to-section edges are traversed to a fixed point with cycle protection. Extra selected sections must also have proven dependency closure. A partial selector must contain every needed section and have no unknown edge; a whole-file/all-sections selection remains the safe alternative, including for storefront operations without a selective proof. The context source's explicit required/supplemental arrays must agree with routing, so dropping a required workflow cannot shrink the proof. Optional supplemental workflows do not enlarge the operation's claimed closure; their existing whole-file fallback is retained, as are direct-workflow and untrusted-reader fallbacks. The audit reuses parsed retrieval facts rather than changing the generic reader algorithm.

The manifest's `convention-dependencies` domain binds the two synthetic authorities into projection identity. Operation/workflow ownership is unique; conflicting repeated section definitions fail rather than choosing one silently, while identical section definitions may agree. This is an authored finite fixture contract, not inference from field names, arbitrary prose, or token measurements. The §3.2/§6.1 requirement for an evidenced trusted publication scope still applies; structural closure alone does not authorize a reader to trust selective loading. Final Task 12 matrix review and Task 14 measurement remain open.
